Typy wartościowe a referencyjne w pamięci

To najważniejszy moment zwrotny w całym kursie C#. Prawie każdy początkujący zakłada, że instrukcja var b = a; tworzy niezależną kopię zmiennej. Dla liczb int to prawda. Dla obiektów klas (class) to groźny mit, który prowadzi do najtrudniejszych błędów w grach, sklepach i systemach bankowych.

Po tej lekcji będziesz widzieć pamięć C# jak rentgen: od razu odróżnisz skopiowanie wartości od skopiowania adresu (referencji), opanujesz bezpieczne operatory dla null (?. i ??) i będziesz wiedzieć, kiedy użyć struct, a kiedy class.

🧠 Zderzenie z rzeczywistością: dlaczego zmiana w p2 zepsuła p1?

Porównaj dwa niemal identyczne fragmenty kodu:

// PRZYPADEK A: typ wartościowy (int)
int a = 100;
int b = a;      // Kopiuje samą LICZBĘ 100 do nowego, niezależnego miejsca w pamięci
b = 250;
Console.WriteLine(a); // Wypisze: 100 (a pozostało nietknięte)

// PRZYPADEK B: typ referencyjny (class Produkt)
var p1 = new Produkt("Mysz", 100m);
var p2 = p1;    // NIE tworzy nowego Produktu! Kopiuje wyłącznie ADRES (referencję)!
p2.ZmienCene(250m);
Console.WriteLine(p1.Cena); // Wypisze: 250 (p1 i p2 to dwa piloty do TEGO SAMEGO obiektu!)

🔎 Co dzieje się przy przekazywaniu do metody?

Ten sam mechanizm działa, gdy przekazujesz zmienną jako parametr metody:

static void ZastosujRabat(Produkt p)
{
    // Parametr 'p' otrzymał kopię ADRESU tego samego obiektu!
    p.ZmienCene(p.Cena * 0.9m); // ZMIENIA oryginalny obiekt z Main()!
}

Jeśli przekażesz int cena = 100; do void Podwoj(int x) { x *= 2; }, oryginał w Main() się nie zmieni. Jeśli przekażesz obiekt class, metoda modyfikuje ten sam obiekt w pamięci!

⚠️ Zagadka string oraz bezpieczna praca z null (?. i ??)

🔎 Dlaczego string zachowuje się jak typ wartościowy?

string w C# jest typem referencyjnym, ale jest niemutowalny (immutable). Nie możesz zmienić pojedynczej litery w istniejącym napisie. Gdy piszesz string s2 = s1; s2 = "Nowy";, nie modyfikujesz starego obiektu - tworzysz nowy napis "Nowy" i przepinasz adres w s2, zostawiając s1 bez zmian.

🔎 Bezpieczne operatory null: ?. oraz ??

Gdy zmienna referencyjna ma wartość null, odczyt klient.Imie natychmiast kończy program błędem NullReferenceException. Zamiast rozbudowanych if, C# oferuje dwa eleganckie operatory:

KartaPostaci bohater = null;

// Operator ?. (null-conditional): jeśli bohater == null, zwróć null zamiast rzucać wyjątek!
string imie = bohater?.Imie;

// Operator ?? (null-coalescing): jeśli lewa strona to null, użyj wartości domyślnej z prawej!
string etykieta = bohater?.Imie ?? "Nieznany bohater"; // "Nieznany bohater"

🧱 Kiedy własny struct zamiast class?

W C# możesz definiować własne lekkie typy wartościowe słowem struct (np. public struct Punkt2D { public int X; public int Y; }). Wybierasz struct, gdy typ reprezentuje małą, prostą wartość matematyczną (np. punkt 2D, kolor RGB, wektor), którą chcesz kopiować przy przypisaniu. Dla wszystkich obiektów biznesowych z logiką, tożsamością i dziedziczeniem (KontoBankowe, Produkt, Bohater) wybierasz zawsze class.

🔬 Pod maską: Obalenie mitu „wartości zawsze na stosie”, Boxing i pokolenia Garbage Collectora STOS, STERTA & GC

1. Dlaczego reguła „wartości na stosie, referencje na stercie” jest mitem?
Stos (Stack) i Sterta (Heap) to szczegóły implementacji CLR, a nie definicja typów. Zobacz, gdzie naprawdę lądują dane w 4 typowych sytuacjach:

Deklaracja w C# Rodzaj typu Gdzie fizycznie żyje w pamięci RAM?
int licznik = 5; (zmienna lokalna w metodzie) Wartościowy Stos (w ramce bieżącej metody)
public decimal Saldo (pole wewnątrz class Konto) Wartościowy Sterta (wewnątrz bloku obiektu Konto!)
Zmienna lokalna var k = new Konto(...) Referencyjny Adres (8 B) żyje na Stosie, sam obiekt Konto na Stercie
object boxed = 42; (Boxing!) Wartościowy → zapakowany Sterta (CLR tworzy pudełko na stercie i kopiuje tam 42!)

2. Pułapka Boxingu: pakowanie typu wartościowego (int) do object tworzy nowy obiekt na stercie i obciąża Garbage Collector. Właśnie dlatego w C# używamy generycznych List<int> (zero boxingu!) zamiast przestarzałej ArrayList (która trzymała object).

3. Jak sprząta pokoleniowy Garbage Collector (Gen 0, Gen 1, Gen 2)?
Większość obiektów (np. tymczasowe napisy z jednej metody) ginie po milisekundach. Dlatego GC w .NET dzieli stertę na 3 pokolenia:

  • Gen 0: nowo utworzone obiekty. Sprzątane błyskawicznie (~0.1 ms).
  • Gen 1: obiekty, które przeżyły jedno sprzątanie Gen 0.
  • Gen 2: obiekty długowieczne (np. główny obiekt Bank działający przez cały czas pracy programu).

🦾🐨🦾 Co masz wynieść z tej lekcji:

  • Dla typów wartościowych (int, decimal, bool, struct) przypisanie b = a kopiuje wartość. Dla klas (class) przypisanie b = a kopiuje referencję (adres) do tego samego obiektu.
  • Gdy potrzebujesz niezależnej kopii obiektu, musisz utworzyć nowy egzemplarz przez new (np. metodą Klonuj()).
  • Zamiast ryzykować NullReferenceException, używaj operatorów ?. (bezpieczny dostęp) oraz ?? (wartość domyślna dla null).
