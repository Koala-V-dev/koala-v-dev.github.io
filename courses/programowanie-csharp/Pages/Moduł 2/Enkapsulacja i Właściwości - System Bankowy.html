Enkapsulacja i Właściwości - System Bankowy

W poprzednich lekcjach pisałeś klasy z metodami walidującymi. Została jednak jedna groźna luka: jeśli właściwość ma public set, dowolny inny plik w projekcie może ominąć Twoje metody i wpisać wprost konto.Saldo = -50000m;. Cała Twoja walidacja staje się wtedy bezużyteczna.

Enkapsulacja (hermetyzacja) to nie „pisanie get; set; żeby kompilator nie narzekał”. To zasada projektowania, w której obiekt sam strzeże swoich niezmienników (reguł biznesowych, które muszą pozostać prawdziwe przez cały czas życia obiektu) i nie pozwala żadnemu kodowi z zewnątrz zepsuć swojego stanu.

🔍 Problem z życia: co się psuje, gdy pole ma public set

Spójrz na „naiwny” system bankowy, w którym pole jest otwarte dla wszystkich:

public class ZleKonto
{
    public decimal Saldo { get; set; } // Każdy plik w projekcie może tu wpisać cokolwiek!
}

// W innym pliku programu:
var konto = new ZleKonto();
konto.Saldo = -50000m; // Kompilator na to pozwolił! Niezmiennik został złamany!

🔎 Mapa modyfikatorów dostępu w C#

Aby zamknąć dostęp do stanu obiektu, C# daje cztery poziomy widoczności:

Modyfikator Kto widzi tę składową? Typowe zastosowanie
public Każdy plik w projekcie i poza nim Publiczny interfejs klasy (Wplac(), Wyplac(), odczyt Saldo)
private Wyłącznie wnętrze tej samej klasy Ukryte pola robocze (_saldo, _historia), metody pomocnicze
protected Ta klasa oraz klasy po niej dziedziczące protected set przy Saldo, aby klasa potomna mogła doliczyć odsetki
internal Wszystkie pliki w obrębie tego samego projektu (assembly) Narzędzia wewnętrzne biblioteki

🔎 Auto-property kontra pełna właściwość z polem zapasowym (backing field)

W C# właściwości można zapisać na dwa sposoby:

// Sposób 1: Auto-property (najczystszy i najczęstszy w C#)
// Odczyt z zewnątrz (get), zapis wyłącznie wewnątrz klasy lub klas potomnych (protected set)
public decimal Saldo { get; protected set; }

// Sposób 2: Pełna właściwość z prywatnym polem zapasowym (_pin) i walidacją w setterze
private string _pin;
public string Pin
{
    get { return _pin; }
    set
    {
        if (string.IsNullOrWhiteSpace(value) || value.Length != 4)
            throw new ArgumentException("PIN musi składać się z 4 znaków.");
        _pin = value;
    }
}

⚠️ Pułapka: { get; } kontra { get; protected set; }

  • public string Wlasciciel { get; } oznacza właściwość tylko do odczytu (read‑only): można ją ustawić wyłącznie raz w konstruktorze (właściciel konta nie zmienia się przy każdej transakcji).
  • public decimal Saldo { get; protected set; } pozwala każdemu odczytać saldo (konto.Saldo), ale zmienić je mogą wyłącznie metody wewnątrz klasy (np. Wplac, Wyplac) oraz klasy dziedziczące, które poznasz w kolejnej lekcji.
🔬 Pod maską: Backing field, metody get_Saldo/set_Saldo w CIL i jak działa test Refleksji KOMPILATOR & REFLEKSJA

Właściwość automatyczna public decimal Saldo { get; protected set; } wcale nie jest specjalnym typem zmiennej w pamięci procesora. Kompilator C# podczas budowania pliku .dll automatycznie rozwija tę jedną linijkę do prywatnego pola o specjalnej, niedostępnej w C# nazwie oraz dwóch prawdziwych metod w kodzie pośrednim CIL:

// Kod generowany przez kompilator C# pod maską:
private decimal <Saldo>k__BackingField;

public decimal get_Saldo()
{
    return this.<Saldo>k__BackingField;
}

protected void set_Saldo(decimal value)
{
    this.<Saldo>k__BackingField = value;
}

Dlatego w zadaniu praktycznym poniżej piąty test jednostkowy używa Refleksji (System.Reflection):

var prop = typeof(KontoBankowe).GetProperty("Saldo");
// Odczytujemy metadane skompilowanej metody set_Saldo:
bool czyChronione = prop != null && (prop.SetMethod == null || !prop.SetMethod.IsPublic);

Refleksja zagląda wprost do tablicy metadanych skompilowanej klasy. Jeśli uczeń spróbuje „ułatwić” sobie zadanie i zmieni protected set na public set, test refleksji natychmiast wykryje naruszenie enkapsulacji!

🧩 Rozgrzewka decyzyjna: mechanizm enkapsulacji i jego rola

Połącz każdy element klasy KontoBankowe z problemem inżynierskim, który rozwiązuje:

💻 Zadanie praktyczne (projekt 2-plikowy): Hermetyczne KontoBankowe

W poniższym edytorze masz dwa osobne pliki - dokładnie jak w prawdziwym projekcie Visual Studio / Rider:

  • Program.cs - kod klienta korzystający z konta.
  • KontoBankowe.cs - definicja Twojej klasy (kliknij tę zakładkę!).

Uzupełnij w KontoBankowe.cs trzy miejsca oznaczone TODO:

  1. Konstruktor KontoBankowe(string wlasciciel, decimal saldoPoczatkowe = 0m):
    • jeśli string.IsNullOrWhiteSpace(wlasciciel) → rzuć throw new ArgumentException("Brak właściciela");,
    • jeśli saldoPoczatkowe < 0m → rzuć throw new ArgumentOutOfRangeException(nameof(saldoPoczatkowe));.
  2. Metoda Wplac(decimal kwota):
    • jeśli kwota <= 0m → rzuć throw new ArgumentOutOfRangeException(nameof(kwota));,
    • w przeciwnym razie zwiększ Saldo += kwota;.
  3. Metoda public virtual bool Wyplac(decimal kwota):
    • jeśli kwota <= 0m → rzuć throw new ArgumentOutOfRangeException(nameof(kwota));,
    • jeśli kwota > Saldo → zwróć false (nie zmieniaj Saldo),
    • w przeciwnym razie odejmij Saldo -= kwota; i zwróć true.

Sprawdź rozwiązanie po wykonaniu próby 
public class KontoBankowe
{
    public string Wlasciciel { get; }
    public decimal Saldo { get; protected set; }

    public KontoBankowe(string wlasciciel, decimal saldoPoczatkowe = 0m)
    {
        if (string.IsNullOrWhiteSpace(wlasciciel)) throw new ArgumentException("Brak właściciela");
        if (saldoPoczatkowe < 0m) throw new ArgumentOutOfRangeException(nameof(saldoPoczatkowe));
        Wlasciciel = wlasciciel;
        Saldo = saldoPoczatkowe;
    }

    public void Wplac(decimal kwota)
    {
        if (kwota <= 0m) throw new ArgumentOutOfRangeException(nameof(kwota));
        Saldo += kwota;
    }

    public virtual bool Wyplac(decimal kwota)
    {
        if (kwota <= 0m) throw new ArgumentOutOfRangeException(nameof(kwota));
        if (kwota > Saldo) return false;
        Saldo -= kwota;
        return true;
    }
}

🦾🐨🦾 Co masz wynieść z tej lekcji:

  • Gdy pole reprezentuje stan krytyczny obiektu (np. saldo, liczba żyć, stan magazynu), nigdy nie dawaj mu public set - chroń je przez protected set lub private set i zmieniaj wyłącznie metodami z walidacją.
  • Konstruktor z Guard Clause gwarantuje, że w pamięci programu nie może powstać obiekt w niepoprawnym stanie.
  • Słowo virtual przy metodzie Wyplac otwiera drogę do kolejnego filaru OOP: dziedziczenia i polimorfizmu.
