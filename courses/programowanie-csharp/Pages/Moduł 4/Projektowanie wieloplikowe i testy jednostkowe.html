Projektowanie wieloplikowe i testy jednostkowe

Przez cały kurs klikałeś przycisk Sprawdź testy i widziałeś zielone albo czerwone komunikaty. Czas zajrzeć na drugą stronę lustra i nauczyć się myśleć jak inżynier projektujący testy jednostkowe (Unit Tests) - bo w prawdziwej pracy programisty (oraz na egzaminie INF.04) to Ty udowadniasz, że Twój kod działa dla każdego nietypowego przypadku.

🧪 Anatomia profesjonalnego testu: wzorzec AAA

Dobry test jednostkowy sprawdza jedną konkretną regułę biznesową i dzieli się zawsze na trzy czytelne sekcje AAA:

// 1. ARRANGE (Przygotowanie): tworzymy obiekty i dane wejściowe
var konto = new KontoBankowe("Jan", 100m);

// 2. ACT (Działanie): wywołujemy dokładnie JEDNĄ badaną operację
bool wynik = konto.Wyplac(40m);

// 3. ASSERT (Weryfikacja): sprawdzamy wynik i nowy stan obiektu
LabAssert.True(wynik);
LabAssert.Equal(60m, konto.Saldo);

🎯 Lista kontrolna przypadków brzegowych (Edge Cases)

Początkujący testują tylko tzw. Happy Path (ładne, poprawne dane, np. 100 zł). Prawdziwe błędy w oprogramowaniu kryją się niemal wyłącznie na granicach:

Kategoria danych Przypadki brzegowe, które MUSISZ sprawdzić
Liczby (int, decimal) 0, wartości ujemne (-1, -0.01m), wartość dokładnie na progu (np. 150m przy progu >= 150m)
Napisy (string) null, pusty napis "", same spacje " " (string.IsNullOrWhiteSpace)
Kolekcje (List<T>, T[]) null, pusta lista (Count == 0), lista z 1 elementem, duplikaty
Obiekty i operacje Próba usunięcia nieistniejącego elementu, wielokrotne wywołanie tej samej metody
🔬 Pod maską: Piramida testów, pułapka 100% Code Coverage i testowanie mutacyjne INŻYNIERIA JAKOŚCI

1. Dlaczego 100% pokrycia kodu (Code Coverage) nie gwarantuje braku błędów?
Spójrz na metodę CzyDarmowaDostawa(decimal kwota) => kwota >= 150m;. Jeśli napiszesz tylko dwa testy: dla 100m (false) oraz dla 200m (true), narzędzie raportujące pokaże 100% pokrycia linii. A jednak gdyby ktoś przypadkiem zmienił kod na kwota > 150m (zgubił znak równości!), oba testy nadal byłyby zielone!

2. Myślenie mutacyjne (Mutation Testing, np. narzędzie Stryker.NET):
Profesjonalny automat wprowadza do Twojego kodu celowe uszkodzenia (mutanty):

Oryginalny kod Wprowadzony mutant Który test go zabije?
kwota >= 150m kwota > 150m Wyłącznie test dla dokładnej granicy 150m!
Saldo - kwota < -Limit Saldo - kwota <= -Limit Wyłącznie test schodzący dokładnie do -Limit!
if (kwota <= 0m) throw if (kwota < 0m) throw Wyłącznie test sprawdzający kwota == 0m!

Wniosek zmieniający model myślowy: pisząc testy, zawsze pytaj siebie: „jeśli ktoś zmieni >= na > albo usunie warunek == 0, czy któryś mój test zrobi się czerwony?”. Jeśli nie - dopisz test na dokładną wartość graniczną!

W pliku KoszykZakupowy.cs zaimplementuj klasę, która przejdzie surowy zestaw testów Happy Path oraz Edge Cases:

  1. DodajPozycje(string nazwa, decimal cena, int ilosc):
    • jeśli string.IsNullOrWhiteSpace(nazwa) → rzuć ArgumentException,
    • jeśli cena <= 0m lub ilosc <= 0 → rzuć ArgumentOutOfRangeException,
    • jeśli produkt o tej samej nazwie (bez rozróżniania wielkości liter lub dokładnie) już jest w koszyku, zwiększ jego ilość zamiast duplikować wpis; inaczej dodaj nową pozycję.
  2. UsunPozycje(string nazwa):
    • jeśli produkt istnieje w koszyku, usuń go i zwróć true; jeśli nie istnieje (lub nazwa jest pusta/null), zwróć false bez rzucania wyjątku.
  3. ObliczSume():
    • zwróć łączną wartość wszystkich pozycji (cena * ilosc), a dla pustego koszyka zwróć 0m.

public void DodajPozycje(string nazwa, decimal cena, int ilosc)
{
    if (string.IsNullOrWhiteSpace(nazwa)) throw new ArgumentException("Brak nazwy produktu.");
    if (cena <= 0m) throw new ArgumentOutOfRangeException(nameof(cena));
    if (ilosc <= 0) throw new ArgumentOutOfRangeException(nameof(ilosc));

    foreach (var p in _pozycje)
    {
        if (p.Nazwa == nazwa)
        {
            p.Ilosc += ilosc;
            return;
        }
    }
    _pozycje.Add(new PozycjaKoszyka(nazwa, cena, ilosc));
}

public bool UsunPozycje(string nazwa)
{
    if (string.IsNullOrWhiteSpace(nazwa)) return false;
    for (int i = 0; i < _pozycje.Count; i++)
    {
        if (_pozycje[i].Nazwa == nazwa)
        {
            _pozycje.RemoveAt(i);
            return true;
        }
    }
    return false;
}

public decimal ObliczSume()
{
    decimal suma = 0m;
    foreach (var p in _pozycje)
    {
        suma += p.Cena * p.Ilosc;
    }
    return suma;
}

🦾🐨🦾 Co masz wynieść z tej lekcji:

  • Każdy test jednostkowy układaj w strukturze AAA (Arrange → Act → Assert) i sprawdzaj w nim dokładnie jedną regułę biznesową.
  • Oprócz ścieżki poprawnej (Happy Path) zawsze testuj przypadki brzegowe: 0, liczby ujemne, dokładnie na granicy progu, null, puste napisy i puste kolekcje.
  • Dobre testy jednostkowe to Twoja sieć bezpieczeństwa - pozwalają śmiało refaktoryzować kod bez obawy, że zepsujesz działające funkcje.
