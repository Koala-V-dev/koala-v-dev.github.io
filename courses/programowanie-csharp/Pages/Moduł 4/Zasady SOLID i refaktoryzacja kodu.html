Zasady SOLID i refaktoryzacja kodu

Napisanie programu, który „jakoś działa dzisiaj”, to dopiero połowa roboty inżyniera. Prawdziwy test przychodzi po trzech miesiącach, gdy klient prosi o dopisanie nowego rodzaju rabatu, nowego typu płatności albo nowego formatu raportu. Jeśli każda zmiana zmusza Cię do rozgrzebywania 400‑linijkowego if / else if, Twój kod jest kruchy.

W tej lekcji poznasz trzy najważniejsze w codziennej pracy zasady SOLID (SRP, OCP, DIP) i na własnych oczach zmienisz sztywny kalkulator w elastyczną architekturę opartą na wzorcu Strategia (Strategy).

🚨 Diagnoza złego kodu: łamanie OCP przez rosnący if / else

Spójrz na kod sklepu, który na pierwszy rzut oka wygląda niewinnie:

public class KalkulatorCeny
{
    public decimal Oblicz(decimal cena, string typKlienta)
    {
        if (typKlienta == "VIP") return cena * 0.80m;
        else if (typKlienta == "Student") return cena * 0.90m;
        else if (typKlienta == "BlackFriday") return cena * 0.70m;
        else return cena;
    }
}

Co jest nie tak z tym kodem?

  1. Gdy marketing wymyśli 10 nowych promocji, musisz za każdym razem edytować działającą klasę KalkulatorCeny (ryzykując zepsucie rabatu dla VIP‑a!).
  2. Literówka "vip" zamiast "VIP" przechodzi przez kompilator bez ostrzeżenia i cicho nie nalicza rabatu.

🏛️ Trzy filary czystej architektury (SRP, OCP, DIP)

Zasada Pełna nazwa Reguła decyzyjna dla Twojego kodu
SRP Single Responsibility Principle Jedna klasa ma jeden powód do zmiany. KontoBankowe nie wysyła e‑maili ani nie zapisuje do bazy danych.
OCP Open/Closed Principle Kod powinien być otwarty na rozszerzanie (dodanie nowej klasy RabatVip : IRabat), ale zamknięty na modyfikacje istniejącego rdzenia (Kasa).
DIP Dependency Inversion Principle Klasa wyższego poziomu (Kasa) zależy od interfejsu (IRabat), a nie od konkretnej klasy (RabatStudent). Zależność przekazujesz przez konstruktor!

🔍 Wzorzec Strategia (Strategy) w praktyce

Zamiast if (typKlienta == "VIP"), tworzysz interfejs IRabat i przekazujesz wybraną strategię do Kasy:

public interface IRabat
{
    decimal Zastosuj(decimal cena);
}

public class RabatProcentowy : IRabat
{
    public decimal Procent { get; }
    public RabatProcentowy(decimal procent) { Procent = procent; }
    public decimal Zastosuj(decimal cena) => cena * (1m - Procent);
}

public class Kasa
{
    private readonly IRabat _strategiaRabatu;

    // DIP: Wstrzykujemy interfejs przez konstruktor (Dependency Injection)!
    public Kasa(IRabat strategiaRabatu)
    {
        _strategiaRabatu = strategiaRabatu ?? throw new ArgumentNullException(nameof(strategiaRabatu));
    }

    public decimal ObliczDoZaplaty(decimal cena) => _strategiaRabatu.Zastosuj(cena);
}

Zauważ przełom: gdy jutro pojawi się RabatKuponowy (odejmujący stałe 20 zł), dopisujesz jedną nową klasę implementującą IRabat - w pliku Kasa.cs nie zmieniasz ani jednego znaku!

🔬 Pod maską: Jak Dependency Injection (DIP) pozwala testować system bez bazy danych i sieci ARCHITEKTURA & TESTY

Wyobraź sobie klasę SerwisPlatnosci, która w środku robi na sztywno var bramka = new PrawdziwyPayU();. Jak napiszesz test jednostkowy dla takiej klasy? Nie możesz - każde uruchomienie testu próbowałoby pobrać prawdziwe pieniądze z karty przez internet!

Gdy zastosujesz DIP (wstrzykiwanie przez konstruktor):

public class SerwisPlatnosci
{
    private readonly IBramkaPlatnosci _bramka;
    public SerwisPlatnosci(IBramkaPlatnosci bramka) { _bramka = bramka; }
}
  • Na produkcji wstrzykujesz new PrawdziwyPayU().
  • W testach jednostkowych wstrzykujesz lekką klasę zastępczą (Stub / Mock), np. new UdawanaBramkaZawszeOk(), która działa w 0.01 ms w pamięci RAM bez połączenia z siecią.

Wniosek inżynierski: dobrze zaprojektowana architektura OOP nie jest „sztuką dla sztuki” - to jedyny sposób, by duży zespół mógł rozwijać i testować aplikację bez paraliżującego strachu przed każdą zmianą.

💻 Zadanie praktyczne (3 pliki): Wzorzec Strategia dla systemu rabatów (OCP + DIP)

W edytorze masz trzy pliki: Program.cs, zablokowane IRabat.cs oraz StrategieRabatu.cs, w którym zaimplementujesz trzy klasy zgodne z OCP i DIP:

  1. BrakRabatu : IRabat:
    • metoda Zastosuj(decimal cena) zwraca po prostu cena bez zmian.
  2. RabatKwotowy : IRabat:
    • konstruktor RabatKwotowy(decimal kwota) - jeśli kwota < 0m, rzuć ArgumentOutOfRangeException,
    • metoda Zastosuj(decimal cena) odejmuje kwota, ale cena po rabacie nigdy nie może spaść poniżej 0m (Math.Max(0m, cena - Kwota)).
  3. Kasa:
    • konstruktor Kasa(IRabat rabat) - jeśli rabat == null, rzuć ArgumentNullException,
    • metoda ObliczDoZaplaty(decimal cena) - jeśli cena < 0m, rzuć ArgumentOutOfRangeException; w przeciwnym razie deleguj do _rabat.Zastosuj(cena).
using System;

class Program
{

        var kasaKupon = new Kasa(new RabatKwotowy(30m));

}

Sprawdź rozwiązanie po wykonaniu próby 
public class BrakRabatu : IRabat
{
    public decimal Zastosuj(decimal cena) => cena;
}

public class RabatKwotowy : IRabat
{
    public decimal Kwota { get; }

    public RabatKwotowy(decimal kwota)
    {
        if (kwota < 0m) throw new ArgumentOutOfRangeException(nameof(kwota));
        Kwota = kwota;
    }

    public decimal Zastosuj(decimal cena) => Math.Max(0m, cena - Kwota);
}

public class Kasa
{
    private readonly IRabat _rabat;

    public Kasa(IRabat rabat)
    {
        _rabat = rabat ?? throw new ArgumentNullException(nameof(rabat));
    }

    public decimal ObliczDoZaplaty(decimal cena)
    {
        if (cena < 0m) throw new ArgumentOutOfRangeException(nameof(cena));
        return _rabat.Zastosuj(cena);
    }
}

🦾🐨🦾 Co masz wynieść z tej lekcji:

  • Gdy widzisz w klasie rosnący łańcuch if (typ == "..."), zastąp go interfejsem i wzorcem Strategia (OCP), aby dodawać nowe zachowania bez ruszania starego kodu.
  • Przekazuj zależności przez interfejs w konstruktorze (DIP / Dependency Injection) - dzięki temu klasa jest niezależna od konkretnej implementacji i błyskawicznie testowalna.
  • Pilnuj zasady SRP: każda klasa odpowiada za jeden konkretny obszar logiki.
