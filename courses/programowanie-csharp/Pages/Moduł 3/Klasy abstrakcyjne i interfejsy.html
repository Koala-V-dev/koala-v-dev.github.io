Klasy abstrakcyjne i interfejsy

Wyobraź sobie, że w Twoim systemie bankowym chcesz generować podsumowanie tekstowe dla zupełnie różnych obiektów: dla konta bankowego, dla faktury i dla karty płatniczej. Faktura nie jest kontem bankowym, więc dziedziczenie Faktura : KontoBankowe nie ma żadnego sensu. Jak sprawić, by jedna pętla foreach potrafiła poprosić każdy z tych obiektów o raport? W C# służą do tego klasy abstrakcyjne i interfejsy.

🏗️ Klasa abstrakcyjna (JEST) kontra Interfejs (POTRAFI)

To rozróżnienie oddziela początkujących od programistów myślących obiektowo:

Mechanizm Relacja Co zawiera? Limit w jednej klasie Kiedy wybierasz?
abstract class JEST (is‑a) Wspólny stan (pola, właściwości), konstruktor oraz metody abstract bez ciała Tylko 1 klasa bazowa Gdy klasy należą do jednej rodziny i dzielą kod (np. KontoOszczednosciowe JEST KontoBankowe)
interface POTRAFI (can‑do) Wyłącznie kontrakt (podpisy metod i właściwości, bez pól stanu) Dowolnie wiele Gdy różne, niespokrewnione klasy muszą spełnić ten sam kontrakt (np. IRaportowalny)

💬 Notatka

W C# nazwy interfejsów z konwencji zawsze zaczynają się od wielkiej litery I (np. IRaportowalny, IPowiadamialny, IComparable).

🔍 Przykład składni interfejsu

// Kontrakt: każda klasa implementująca IRaportowalny MUSI mieć metodę PobierzRaport()
public interface IRaportowalny
{
    string PobierzRaport();
}

public class Faktura : IRaportowalny
{
    public string Numer { get; }
    public decimal Kwota { get; }

    public Faktura(string numer, decimal kwota)
    {
        Numer = numer;
        Kwota = kwota;
    }

    public string PobierzRaport()
    {
        return $"Faktura {Numer}: {Kwota:F2} zł";
    }
}

Klasa abstrakcyjna (public abstract class Dokument) działa podobnie do zwykłej klasy bazowej, z jedną kluczową różnicą: nie możesz zrobić new Dokument() - musisz utworzyć obiekt konkretnej klasy potomnej, która uzupełni wszystkie metody abstract słowem override.

🔬 Pod maską: Problem Diamentu z C++ oraz jak CLR wywołuje metody interfejsów ARCHITEKTURA OOP & CLR

W języku C++ jedna klasa może dziedziczyć jednocześnie po dwóch klasach bazowych:

// Kod C++ (w C# ZABRONIONY przez kompilator!):
class Urzadzenie { public: int Moc; };
class Drukarka : public Urzadzenie {};
class Skaner   : public Urzadzenie {};
class UrzadzenieWielofunkcyjne : public Drukarka, public Skaner {};
// Które pole 'Moc' ma odczytać obiekt? To z Drukarki czy ze Skanera?! (Problem Diamentu)

Twórcy C# rozwiązali Problem Diamentu u źródła, rozdzielając dwa pojęcia:

  1. Dziedziczenie stanu i kodu (class / abstract class) jest ściśle pojedyncze - każda klasa ma dokładnie jednego rodzica, więc układ pól na stercie RAM jest zawsze jednoznaczny.
  2. Dziedziczenie kontraktu (interface) może być wielokrotne (class KontoFirmowe : KontoBankowe, IRaportowalny, IOpodatkowany), ponieważ interfejs nie definiuje pól instancji.

Jak CLR wywołuje metodę przez interfejs?
Ponieważ różne klasy mogą mieć metodę PobierzRaport() pod zupełnie innymi indeksami w swoich tablicach vtable, środowisko .NET używa szybkiego mechanizmu Virtual Stub Dispatch (VSD) - krótkiego, samouczącego się kawałka kodu maszynowego (stub), który zapamiętuje ostatnio widziany typ i kieruje wywołanie w zaledwie kilku cyklach procesora.

public class Paragon : IRaportowalny
{
    public string Sklep { get; }
    public decimal Kwota { get; }

    public Paragon(string sklep, decimal kwota)
    {
        if (kwota <= 0m) throw new ArgumentOutOfRangeException(nameof(kwota));
        Sklep = sklep;
        Kwota = kwota;
    }

    public string PobierzRaport()
    {
        return $"Paragon [{Sklep}]: {Kwota:F2} zł";
    }
}

public class Subskrypcja : IRaportowalny
{
    public string Usluga { get; }
    public decimal Miesiecznie { get; }

    public Subskrypcja(string usluga, decimal miesiecznie)
    {
        if (miesiecznie <= 0m) throw new ArgumentOutOfRangeException(nameof(miesiecznie));
        Usluga = usluga;
        Miesiecznie = miesiecznie;
    }

    public string PobierzRaport()
    {
        return $"Subskrypcja [{Usluga}]: {Miesiecznie:F2} zł/mies.";

🦾🐨🦾 Co masz wynieść z tej lekcji:

  • Wybieraj abstract class, gdy klasy łączy wspólny stan i relacja „JEST”; wybieraj interface, gdy różne klasy mają spełnić ten sam kontrakt „POTRAFI”.
  • Nazwę interfejsu w C# zawsze zaczynaj od litery I (np. IRaportowalny).
  • Kolekcja typu List<IRaportowalny> pozwala polimorficznie przetwarzać zupełnie różne klasy bez konieczności tworzenia sztucznego dziedziczenia.
